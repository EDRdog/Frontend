# 요구사항 (ERD)

ERD = Engineering Requirements Document (DB 관계도 아님). PRD(`docs/product-specs/`)를 만족하려면 무엇이 성립해야 하는지 검증 가능한 기준으로 적는다. 왜 그렇게 정했는지는 ADR(`docs/design-docs/decisions/`).

## 쓰는 법
- 기능 묶음마다 파일 하나(예: `upload.md`). 제목 줄에 PRD 기능 ID 를 적는다(PRD 가 없으면 생략). 파일을 만들면 아래 파일 표에 한 줄 추가한다
- 기준 한 줄 = 표 한 행. ID 는 `영문2~4자-번호` (예: `UP-1`), 사람이 확인하는 기준은 `UP-M1`
- 검증 칸은 테스트를 메서드까지 적는다: `테스트클래스.메서드` 또는 `경로::테스트이름`(저장소 루트 기준 경로). 클래스 이름만 적지 않는다. `미구현` 이면 검증 칸에 `없음` 이라 적는다
- 상태 칸 값: `자동`, `자동 (환경변수 있을 때)`, `수동`, `미구현`, `일부 미구현`, `미충족`(코드가 기준과 다름), `미정`, `해당 없음`
- 구현, 배포, 삭제로 상태가 바뀌면 같은 PR 에서 고친다. `scripts/check-docs.sh` 가 상태 값과 테스트 참조를 검사한다

## 표 모양
| ID | 성립해야 할 것 | 검증 | 출처 | 상태 |
|---|---|---|---|---|
| UP-N | PDF, HWP, HWPX 를 받아 작업을 만든다 | `JobControllerTest.createsJob` | PRD F1 | 자동 |

수동 확인 표:
| ID | 확인할 것 | 방법 | 상태 |
|---|---|---|---|
| UP-MN | 실제 사용자 파일을 읽는다 | 학교 시험지 3개를 올려 화면 확인 | 수동 |

## 이 레포의 사정

**테스트 러너가 없다.** 검증은 `tsc` 타입체크와 빌드 성공, 그리고 사람이 화면을 보는 것이 전부다.
그래서 상태 칸이 `수동` 인 항목이 많다. 억지로 `자동` 이라고 적지 않는다.

검증 칸에 테스트를 적을 수 있게 되면(러너를 들이면) 그때 `자동` 으로 바꾼다.

## 파일
| 파일 | 기능 | 다루는 것 |
|---|---|---|
| `shell.md` | 공통 | 라우팅, 인증·데모, 새로고침, 테마, 반응형 |
| `investigation.md` | 조사 | 알림·호스트·이벤트·사건 목록과 상세 |
| `analysis.md` | 분석 | 관계 그래프, IP·도메인 조회, 위협 지도 |
| `response.md` | 대응·온보딩 | 조치 실행과 결과 폴링, 설치 안내, 알림 설정 |
